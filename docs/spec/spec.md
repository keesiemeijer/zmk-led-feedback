# LED feedback specification

## Status and scope

Proposed behavior for the `main` branch. This is a specification, not a description of the current implementation. Backward compatibility with existing configuration names, keycodes, hooks, or internal code is not required.

The goal is to keep layer feedback, on-demand battery feedback, brightness controls, and display on/off controls, while making connection and low-battery warnings a boot-only, optional feature. Unless explicitly changed below, retain their existing user-facing capabilities; implementation details and configuration names may change. The required-peripherals filter applies to warnings, not to an explicitly requested battery display.

## Decisions and recommendations

The following decisions are confirmed:

1. **Layer changes during warnings:** warnings take priority. Update the active layer normally, but do not interrupt a warning or queue transient layer indications. When the warning ends, show the current layer only if continuous layer display is enabled for it. This prevents a frequently changed layer from hiding a warning or extending its sequence.
2. **Boot duration:** use a fixed 20-second window. This does not guarantee that every peripheral will connect and report in time; see [Timing validation](#timing-validation).
3. **Implementation approach:** rewrite warning arbitration and scheduling as a small, explicit state machine inside the existing module, reusing suitable LED rendering, configuration validation, ZMK event handling, and behavior bindings. Remove the old warning logic and obsolete settings rather than leaving parallel paths. Check carefully that the old warning logic separates cleanly from retained display functionality; if it does not, reassess whether a full module rewrite would be simpler before expanding the scope.
4. **Warning opt-ins:** enable connection and low-battery warnings independently. Both default off, and there is no master warning switch.
5. **Low-battery latch:** remember a valid low-battery report for the current boot even if a later report is healthy or unavailable. Reset the latch on the next boot.
6. **Aggregate battery warning:** complete at most one generic battery-warning sequence per boot, regardless of how many required peripherals report low. An interrupted partial sequence may restart. The user can check individual battery levels on demand.
7. **Interrupted battery warning:** if a connection warning interrupts a battery warning, restart the full battery sequence once the connection warning ends, whether the connection resolves or the boot window ends.
8. **Connection-warning cutoff:** connection warnings only display during the 20-second boot window. Immediately before each red LED update, sample monotonic time as the phase start and check that `phase_start + blink_interval <= deadline`. A phase ending exactly at the deadline counts as complete. Measure the phase duration from the LED update, not from the connection event or when work was scheduled. If the check fails, suppress the phase. A queued but not yet rendered red phase is not an active warning and does not interrupt an active battery warning. At the logical deadline, close connection-warning state and request a strip clear; the physical strip clears when deadline handling runs, subject to normal scheduling latency. Never continue connection-warning output after boot. There is no minimum blink count. Stop immediately if all affected required peripherals reconnect or the display is turned off.
9. **Display off during a battery warning:** cancel an already-started battery-warning sequence without replay, even if it is currently interrupted by a connection warning. A warning that has not started may still be shown if the display is turned back on during boot; otherwise discard it at the deadline.
10. **On-demand displays and brightness:** discard on-demand display requests and brightness previews during warnings. If a warning interrupts an already-visible on-demand display or preview, cancel it without resuming afterward. Brightness keys still change the setting and turn the display on, preserving their existing behavior; show the preview when no warning is active.
11. **Unavailable battery readings:** treat a missing or zero battery reading as unavailable, without an automatic warning. An on-demand battery display shows one LED in the configured no-reading color, blue by default. A genuine 0% reading cannot be distinguished and therefore will not trigger a warning.
12. **Event timing:** determine warning eligibility when the module processes an event. Close the boot window before processing events after the deadline, even if they were queued earlier. Process events in order, giving any known connection warning priority; delayed events may be missed for warnings.
13. **Configuration validation:** fail the build with a clear error for invalid configuration or incorrect formats; do not silently correct them or fall back to another value. Initial brightness must be within its configured limits, and a configured per-layer LED count must not exceed the strip length. Runtime brightness controls still stop at their limits.
14. **Warning timing settings:** use a 500 ms blink interval by default, configurable from 100 to 1,000 ms, and five battery-warning blinks by default, configurable from one to ten. Reject values outside these ranges at build time.
15. **Post-deadline connection state:** disconnections processed at or after the boot deadline update ordinary connection state but cannot start, change, or extend a connection warning. There is no post-deadline connection-warning indication or spillover set.
16. **Battery-warning threshold:** allow `0` to disable warnings and `2-100` to enable them. Reject `1` and other values outside those ranges at build time.
17. **Continuous layer inactivity timeout:** allow continuous layer indication to turn off after a configurable period of 0-60 minutes without key presses. The timeout defaults to `0`, which disables it. For a nonzero timeout, start the timer only after the 20-second boot warning window has closed, any active battery warning has finished, and the display is on. If the display is off, start a fresh timer when it is turned on after those conditions are met. Any key-down event, including modifier-only presses, resets the inactivity timer; key releases do not. Key presses while the display is off count as activity but do not turn it on. Key presses during warnings do not interrupt them.

The open-questions section at the end can be used for any details discovered before or during implementation.

## Configuration

- Provide a connection-warning boolean, default off. Enabling it opts in to connection warnings during boot only.
- Use the low-battery threshold as the separate battery-warning opt-in: `0` (default) disables warnings, and `2-100` enables boot-only warnings when battery monitoring is enabled. Reject `1`, negative values, and values above `100` at build time. On-demand battery display remains available without battery warnings.
- A disabled warning type never occupies the display or blocks the other type. There is no master boot-warning enable option.
- Use one shared required-peripherals setting for connection and low-battery warnings. It must be available even when connection warnings are disabled. Keep the existing `-1` default meaning all configured peripheral slots; otherwise allow a count from zero up to the number of configured slots. Fail the build for other values, including counts above the configured slot count.
- Required device numbers are `1..N` after applying the configured slot-to-device mapping. An empty mapping means the default identity order. A nonempty mapping must contain exactly one comma-separated device number per configured slot, with every number from `1` through the slot count appearing exactly once; reject malformed, duplicate, missing, extra, or out-of-range entries at build time. Optional devices never trigger or block either warning, including when a required device has no battery reading. For example, with slot order `2,1,3` and two required devices, the first two slots are required and the third is optional.
- Validate the formats and allowed values of all applicable configuration options at build time. Report the invalid option and expected format or range; do not silently repair invalid input or substitute a fallback.
- Require minimum brightness, initial brightness, and maximum brightness to be in the range `1-255`, with minimum less than or equal to initial and initial less than or equal to maximum. Fail the build if these constraints are not met; do not clamp the configured initial brightness. Runtime brightness keys still stop at the configured limits.
- For the per-layer LED-count setting, allow `-1` for all LEDs, `0` for the existing cycling behavior, or a positive count no greater than the strip length. Fail the build for other values instead of clamping the configured count. Continue to clamp LED counts returned by runtime layer hooks to the strip length, as in the existing hook behavior.
- Provide a continuous-layer inactivity timeout in whole minutes. `0` (default) disables the timeout. For a nonzero value from `1` to `60`, suppress continuous layer indication after that many minutes without a key press. Start the timer only after the 20-second boot warning window has closed, any active battery warning has finished, and the display is on. If the display is turned on after those conditions are met, start a fresh timer. Any key-down event, including modifier-only presses, resets the inactivity timer; key releases do not. Key presses while the display is off count as activity but do not turn it on. Key presses during warnings do not interrupt them. This affects only continuous layer indication, not warnings, on-demand feedback, brightness controls, or display controls. Reject values outside `0-60` at build time.
- Keep the existing configurable battery threshold and visual encoding unless changed during implementation. A nonzero reported level strictly below the threshold is low; the default threshold of zero disables battery warnings.
- Use a shared warning blink interval of 100-1,000 ms, default 500 ms. Each red or yellow phase and each connection-warning dark phase lasts one interval. Immediately before each connection red output update, sample monotonic `phase_start`; start the phase only if `phase_start + blink_interval <= boot_deadline`. A phase ending exactly at the deadline is complete. Logical connection output closes at the deadline, and the physical strip clears when deadline handling runs, subject to normal work-scheduling latency. The battery warning has 1-10 red/yellow blinks, default 5, with a fixed one-second dark pause between blinks and no trailing pause. A full default sequence lasts nine seconds; the maximum configured sequence lasts 29 seconds. Reject out-of-range values at build time.
- Remove the start-display-off and display-off override options, and remove battery-warning repeat configuration. No compatibility aliases are required.

## Boot and warning lifecycle

- Start the boot window when the module initializes, using monotonic uptime. It is the half-open interval `[start, start + 20 seconds)`. It is not restarted by a peripheral reconnect, display toggle, layer change, or battery event.
- During this window, evaluate connection state and battery reports as they are processed. A required peripheral is missing until known to be connected. Do not wait for all battery reports or for the boot window to expire before responding to an eligible warning.
- Initialize connection tracking so an early connection is not missed and a connected required peripheral does not remain falsely marked missing. Verify the Bluetooth callback registration and state initialization order during implementation. If existing connections must be discovered separately, ensure that discovery cannot overwrite newer connection events; choose the mechanism during implementation.
- Use monotonic time when the module processes an event to determine whether it falls inside the window. Before processing the first event or scheduled work at or after the deadline, close the boot window using the connection state already processed during boot. A delayed event processed at or after the deadline is ineligible to create a warning, even if it was queued or received earlier; individual event timestamps are not needed. Continue updating ordinary connection and battery state for on-demand feedback. Process connection and battery events in order; a known connection warning takes priority. If a low-battery warning starts before a disconnection is processed, the connection warning interrupts it and the full battery warning restarts afterward.
- Connection warnings have priority over low-battery warnings only after a complete red phase has been admitted and rendered. A required peripheral disconnect inside the window creates a pending render attempt. Immediately before issuing red output, sample monotonic time and start the phase only if a full configured blink interval fits before the deadline (`phase_start + blink_interval <= deadline`). A phase ending exactly at the deadline counts as complete; no trailing dark phase is required after the last red phase. A queued phase that fails this final time check is suppressed and does not interrupt battery feedback. A new disconnection inside the window creates a pending attempt if no warning is active; an additional disconnection while it is active does not restart the phase. Stop when all missing required peripherals reconnect. At the logical deadline, close connection-warning state and request a strip clear, subject to normal work-scheduling latency. No connection warning starts or continues after the deadline, and there is no minimum blink count. Turning the display off also stops the warning immediately, without replay.
- A valid low-battery report from a required peripheral during the window latches one pending, aggregate battery warning for that boot. Missing, unknown, or unavailable battery readings are not low-battery reports and never produce a warning. A later healthy or missing reading does not erase an already latched report. Reports from optional peripherals and reports at or after the deadline do not create or extend a warning.
- If no rendered connection warning is active, start the pending battery warning immediately. Otherwise start it as soon as the connection warning ends, including when connection output stops at the deadline. Show one full battery warning, even if it runs past the deadline.
- At most one full aggregate battery-warning sequence completes per boot, irrespective of how many required peripherals report low or how many low reports arrive. An interrupted partial sequence may restart as described below, but there are no reminder blinks or repeated completed sequences. Once finished, further low reports in that boot do not start another sequence.
- If a connection warning is rendered during a battery warning, interrupt the battery sequence immediately. When the connection warning ends, restart the battery sequence from the beginning. Previously displayed partial blinks may therefore appear again. A connection event whose red phase is suppressed for insufficient remaining time does not interrupt or restart the battery sequence.
- After the deadline, ignore new battery reports and disconnections for warning purposes. No connection warning may start or remain active. An already-latched battery warning may start when the boot deadline closes the connection-warning opportunity, and an eligible battery warning may continue after it. After warnings finish, ordinary feedback resumes.

ZMK v0.3 forwards a battery level of zero both for a real 0% report and on peripheral disconnect. Its battery event contains no validity flag, and queued events cannot reliably be classified using connection state at processing time. Treat zero as unavailable for warnings and on-demand battery display; document that this can hide a genuine 0% reading. See the [ZMK Bluetooth central](https://github.com/zmkfirmware/zmk/blob/v0.3/app/src/split/bluetooth/central.c) and [battery event definition](https://github.com/zmkfirmware/zmk/blob/v0.3/app/include/zmk/events/battery_state_changed.h).

## Display arbitration

The priority order is:

1. Display off: the strip remains dark, regardless of all other state.
2. Rendered boot connection warning. A queued candidate is not active and only takes priority after its full red phase passes the render-time deadline check.
3. Boot low-battery warning, including its permitted continuation after boot.
4. On-demand battery display and layer feedback under their normal non-warning rules.

The display starts enabled after every boot. It may still be turned off and on with the display controls. While off, no feedback, including boot warnings, layer indications, battery displays, and previews, may light the strip. There are no display-off overrides.

Turning the display off immediately stops visible output. An already-started battery-warning sequence is canceled and considered consumed: do not replay it on re-enable, even if it was interrupted. A low report received while off can be latched but cannot begin while off. If the display is turned back on before the deadline, evaluate the current connection state and any unconsumed pending battery warning immediately; if still off at the deadline, discard the pending warning. Turning the display on after the deadline never starts a missed warning. Connection state and the boot clock continue to advance while off.

While a warning is active, on-demand layer or battery display requests and brightness previews do not take over the strip and are not queued. If a warning begins while an on-demand display or preview is visible, cancel the display or preview immediately; do not resume it after the warning. Controls still update their underlying settings, including brightness or continuous-layer mode. Brightness keys change the setting and turn the display on if it is off. This is an explicit user action, not an override that displays feedback while the display remains off. If turning it on makes a warning eligible, show the warning instead of the brightness preview.

When the display is on and no warning is active, layer indications, on-demand displays, and brightness previews work normally, including during boot.

When a warning ends, start any eligible pending warning first. If no warning remains and the display is on, render the current continuous layer if enabled for that layer. Start its inactivity timer only after the 20-second boot warning window has closed and no warning remains. If the display is off, start a fresh timer when it is turned on after those conditions are met. Otherwise leave the strip dark until a new ordinary feedback request or layer change. Do not replay layer changes, on-demand displays, or previews that occurred during warnings.

## Expected warning appearance

- Connection warning: retain the existing red blinking convention, including the highest-numbered missing required device and the generic warning when the strip cannot identify all configured peripheral slots. Update the indication as missing devices change during boot. A red phase only starts if a full configured interval fits at the time the LED update is issued; a phase ending exactly at the deadline counts as complete. Connection-warning output does not continue after boot.
- Low-battery warning: retain the existing generic red/yellow sequence, using at most four LEDs. It does not identify a particular peripheral. On-demand battery display can be used after the warning to inspect devices.
- Missing or zero battery readings never produce a battery warning. On request, show one LED in the configured no-reading color, blue by default.

## Acceptance tests

Use a controllable monotonic clock and simulated connection, battery, display, and layer events for deterministic state-machine tests. Verify LED output as well as pending and scheduled work, especially at the deadline.

- With both warning options at their defaults, missing connections and low reports never create warnings before or after 20 seconds. On-demand battery display works when battery feedback is enabled and its warning threshold is zero.
- With warnings enabled, a missing required device is indicated when at least one full red phase fits within the deadline, tracks connection changes, and clears when all missing required devices reconnect. Immediately before each red LED update, sample `phase_start` and test `phase_start + blink_interval <= deadline`: a phase ending exactly at the deadline is complete; one that would end later is not started. Include a test where connection work is queued with enough time remaining but handled too late to fit the full phase; it must not render or interrupt an active battery warning. Logical warning state closes at the deadline, and the strip clears when deadline handling runs, subject to normal scheduling latency. A disconnect at or after the deadline does not start or extend a warning.
- Test connection tracking during initialization, including a peripheral that connects as early as the platform allows. Verify that it is not left falsely marked missing and that connection changes during any initial state discovery are not overwritten by stale state.
- A low report with no active connection warning starts a full battery sequence immediately, including when it is processed just before the deadline. A report processed at the deadline does not start one.
- A battery report queued or received before the deadline but processed at or after it does not start a warning. Test connection and low-battery events in both processing orders: a rendered connection warning takes priority, and a battery warning started first is interrupted and later restarted in full. A queued connection phase that fails its render-time fit check does not preempt battery output.
- A low report during a rendered connection warning is shown as one full sequence as soon as all required devices connect or when connection-warning output stops at the deadline. A suppressed, not-yet-rendered connection attempt does not delay or interrupt the battery warning. Additional reports do not restart or repeat it.
- Low reports from multiple required peripherals, including reports after the battery warning finishes, do not produce another warning during the same boot.
- A low report followed by a healthy or unavailable reading while the battery warning is pending still produces the warning. A new boot starts with no latched report.
- A zero battery event or missing reading never triggers a battery warning, including when a peripheral is connected. An on-demand battery display shows one LED in the configured no-reading color for either case. A nonzero report below the threshold still triggers a warning.
- Verify that thresholds `0`, `2`, and `100` are accepted and that `1`, negative values, and values above `100` fail the build. With threshold `2`, a valid 1% report triggers a warning; zero remains unavailable.
- Verify blink interval defaults and bounds of 500 ms and 100-1,000 ms, and battery blink count defaults and bounds of 5 and 1-10. Values outside either range fail the build. Verify nine seconds for the default full battery sequence and 29 seconds for the maximum sequence, with no trailing pause.
- A connection lost while the battery warning is running preempts it. Verify that the complete battery sequence restarts when the connection resolves before the deadline and, separately, when the connection remains unresolved until the connection warning ends at or beyond the deadline. Partial battery blinks may repeat, but no second complete sequence follows.
- A required peripheral disconnecting near the deadline starts a connection warning only if a full configured red phase fits at the moment the LED update is issued. Verify an exact-fit phase is allowed and an overrun phase is suppressed, without truncation. At the logical deadline, close connection-warning state and request a strip clear; there is no minimum number of phases or continuation. Reconnecting before the deadline or turning the display off stops it immediately. A pending battery warning follows when rendered connection output ends, unless the display is off.
- If a second required peripheral disconnects while a connection warning is active, update the indication without restarting the current phase. A disconnect processed at or after the deadline does not change warning output.
- Test that a disconnection processed at or after the deadline does not start, restart, or extend connection-warning output. All late events still update ordinary connection state for post-boot feedback.
- If deadline work runs late and a connection event is processed first at or after the deadline, close boot using the previously processed connection state before applying that event. A delayed pre-deadline event may be missed for warnings, but ordinary connection and battery state remains current for on-demand feedback. Test connection work queued with enough time remaining but handled too late for a complete red phase; it must not render or preempt battery feedback.
- Missing battery reports, optional-device low reports, optional-device disconnections, and disabled warning types never cause or block a warning. Test zero required devices, all required devices, and a non-identity slot mapping. Verify battery warnings still work with connection warnings disabled.
- Layer changes, manual battery requests, and brightness previews never interrupt warnings or replay afterwards. Continuous layer feedback resumes with the latest active layer after the warning. With no warning active and the display on, these displays work normally during boot.
- Verify that timeout values `0`, `1`, and `60` are accepted and values below `0` or above `60` are rejected at build time. With the timeout set to `0`, continuous layer indication does not time out. With a nonzero timeout, verify that the timer does not start before the 20-second boot window closes, while a battery warning is active, or while the display is off. It starts only when the boot window is closed, no warning remains, and the display is on; it turns the indication off after the configured period without key presses. Any key-down event, including a modifier-only press, restores the indication for the current layer and restarts the timer. A key press during a warning does not interrupt it. A key press while the display is off does not turn it on, and turning the display back on after the other conditions are met starts a fresh timeout period. Verify that only continuous layer indication is affected.
- When a warning starts during an on-demand battery display or brightness preview, it immediately cancels that display without resuming it later. A brightness change already made remains in effect.
- Brightness keys change the brightness and turn an off display on. Show the preview when no warning is active; if turning the display on makes a boot warning eligible, show that warning instead and do not replay the preview.
- Display off suppresses every output. Turning it off cancels an already-started battery sequence, including one interrupted by a connection warning, without replay. Turning it on before the deadline re-evaluates an active connection and any battery warning that had not started. A warning missed while still off at the deadline is not replayed after boot.
- After boot, low reports, disconnections, reconnections, display toggles, and layer changes cannot make new warnings eligible. A previously eligible warning may start or continue as specified. Normal layer and requested battery feedback remain usable, including for optional peripherals.
- Verify configuration builds with both warning types disabled, each type independently enabled, and both enabled. Update configuration validation and remove tests for deleted options; run a representative ZMK firmware build.
- Verify valid identity and non-identity slot mappings and required counts of `-1`, zero, and the configured slot count. Invalid formats, duplicate or out-of-range device numbers, wrong mapping lengths, and required counts above the slot count fail the build with a clear error. Test invalid formats and values for other applicable configuration options as well.
- Verify that minimum, initial, and maximum brightness values within `1-255` and in order are accepted; reject invalid ordering or values outside that range. Brightness keys stop at the configured bounds. Accept per-layer LED counts of `-1`, `0`, and the strip length; reject counts above the strip length. Runtime layer-hook counts remain clamped to the strip length.

## Timing validation

On representative hardware, record monotonic times from module initialization to each required peripheral's connection and first valid battery report. Test multiple cold boots and power cycles, already-awake and sleeping peripherals, staggered power-on, and normal reconnect conditions. Record late or missing reports as well as successful timings; do not infer a maximum from one run. Check how often the fixed 20-second window captures the intended warning opportunities in normal use. Battery reports processed at or after the deadline do not trigger warnings. Deadline transitions run when the module's scheduled work is processed and are subject to normal scheduling delays.
